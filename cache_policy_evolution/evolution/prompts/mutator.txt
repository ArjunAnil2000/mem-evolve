FATAL PITFALLS (READ BEFORE WRITING ANY CODE)
============================================================================

A. `is_folio_relevant(folio)` is NOT a hot/cold signal. It returns true
   for EVERY file under the watched directory — including scan files.
   Splitting into "hot_list" (relevant) vs "cold_list" (not relevant)
   gives zero separation. If you want to distinguish within watched
   pages, use a signal OTHER than `is_folio_relevant` — e.g., track
   access counts per inode, per-(inode,pgoff) metadata, reuse distance,
   or file size heuristics.

B. Do NOT manage non-watchlisted pages in your own BPF lists. Non-relevant
   folios are the benchmark process's binary / libc / anon pages; these
   CANNOT be evicted safely. Feeding them into your lists causes reclaim
   loops and full-timeout stalls. Always keep the seed's early return:
   `if (!is_folio_relevant(folio)) return;`

C. `INT64_MAX` is unavailable in BPF. Use `0x7fffffffffffffffLL` instead.

D. The BPF verifier rejects unbounded loops. All iteration must use
   `bpf_for` / `bpf_repeat` with a compile-time bound, or walk fixed
   struct chains. When in doubt, cap loops at 64 and early-exit.

E. Timeouts are a failure. A policy that hangs for 180s is strictly worse
   than one that scores near the seed.

F. BPF globals the loader reads via `skel->bss->NAME` MUST be declared as
   mutable (non-const, non-static-at-file-scope-with-initializer-only)
   and MUST actually be referenced by BPF code. Examples:

     // GOOD — lands in .bss, accessible as skel->bss->g_promotions
     __u64 g_promotions;           // file-scope, no initializer
     __u64 g_evictions = 0;        // initialized to 0 → still .bss

     // BAD — skel has no ->bss member; loader won't compile
     static const __u64 g_promotions = 0;   // const → .rodata
     // (or: variable declared but never used → optimized out entirely)

   If you introduce a counter, (1) declare it at BPF file scope without
   `const`, (2) increment it from at least one struct_ops handler, and
   (3) read it in the loader as `skel->bss->NAME`. Forgetting any of
   these three steps breaks the build or the counter read.

G. Never remove or bypass the vulcan_bpf scaffolding (the includes, the
   `folio_metadata`/`vulcan` struct embedding, the `vulcan_*` calls in
   folio_added/accessed/evicted). A mutation that drops vulcan_bpf usage
   is out of scope for this run, even if it would score well.

J. NEVER use `/` or `%` directly on a signed 64-bit value (`s64`) — this
   includes every accessor return (`vulcan_ewma_get`, `vulcan_get_ewma`,
   `vulcan_get_avg`, `vulcan_minmax_get_min/max`, any local `s64
   threshold`/`interval` variable derived from them). clang-14's BPF
   backend cannot lower signed 64-bit division/modulo at all — it is a
   hard compiler crash ("Unsupport signed division for DAG: ... sdiv ...
   Please convert to unsigned div/mod"), not a verifier warning, and it
   kills the whole compile even if the division looks harmless (e.g.
   averaging two intervals with `/ 2`).
   Fix, in order of preference:
     1. Use the `vulcan_sdiv(a, b)` helper — it is ALREADY in
        `vulcan_bpf.h` (vulcan_bpf.h itself is built on it: see
        `vulcan_ewma_update`/`vulcan_avg_get`), takes two `s64` and
        returns their signed quotient via unsigned division internally,
        and is the drop-in, no-math-required replacement for `a / b`:
          s64 avg_interval = vulcan_sdiv(min_interval + max_interval, 2);
        This is correct for ANY divisor, not just powers of 2, and needs
        no manual shift/scale work. Prefer this over options 2/3 below —
        it's what the library itself uses internally to survive this
        exact clang-14 limitation.
     2. There is no `vulcan_smod` — signed `%` has no equivalent helper.
        If both operands are provably non-negative (interval/timestamp
        deltas always are), cast to `u64` first: `(u64)a % (u64)b`.
     3. Only if you specifically want a fast power-of-2 divide (not a
        general one), a right-shift is fine and cheaper than a function
        call: `x >> 1` for `/2`, `x >> 2` for `/4`, etc. — or a
        shift-scaled multiply for an arbitrary ratio, e.g. `(x * 5) >> 3`
        for roughly `x * 0.625`. This is an established pattern in this
        codebase's own evolved policies (search "avoid division" in prior
        winning policies for a worked example) but `vulcan_sdiv` covers
        the same case with less arithmetic to get wrong — use it unless
        you have a specific reason to want the shift instead.
   Do not "just try `/` and see if it compiles" — it will not, every
   time, for every signed division, regardless of the divisor.

K. Per-folio interval state has exactly two fields, not four:
   `struct vulcan_folio_metadata` only embeds `interval_minmax` (`struct

POLICY METRICS — FEEDBACK CONVENTION (zero per-access overhead)
============================================================================

Your loader can dump named state to `$POLICY_METRICS_OUT` on exit. The
evaluator reads it and surfaces the values in next-round feedback under
`policy_counters:`. Use this to introspect your own state machine across
rounds without any workload cooperation.

The helper is in `evo_dump.h`. Pattern:

    // In USERSPACE LOADER section:
    #include "evo_dump.h"
    ...
    while (!exiting) sleep(1);

    FILE *m = evo_metrics_open();
    evo_dump_u64(m, "small_list_size",   skel->bss->small_list_size);
    evo_dump_u64(m, "main_list_size",    skel->bss->main_list_size);
    evo_dump_u64(m, "g_ghost_hits",      skel->bss->g_ghost_hits);
    evo_metrics_close(m);

    ret = 0;

Cost model — read carefully:

  * Each `evo_dump_u64(...)` is a single fread of an existing BPF global
    AT EXIT TIME. Zero per-access overhead. Surface as much as you want.
  * If you want event counts (evictions, promotions, ghost_hits), declare
    them as plain `__u64 g_NAME;` BPF globals and bump them in your hooks.
    This costs roughly one cache-line write per access on a single CPU —
    real, but small (much less than a hash-map lookup).
  * Do NOT add `__sync_fetch_and_add` on a shared global counter that
    every CPU touches — cross-CPU cache-line bouncing eats throughput.
    If you really need atomicity, use a per-CPU map; otherwise just live
    with the small race (counters are diagnostic, not state-of-truth).

Useful things to dump:
  * Sizes of any list/queue your policy maintains (`small_list_size`,
    `protected_list_size`, etc.).
  * Counters of events fired during the run (`g_evictions`, `g_ghost_hits`,
    `g_promote_skipped_unread`).
  * Tunables you want to confirm landed in `.rodata` correctly
    (`skel->rodata->cache_size`, `skel->rodata->small_target_pct`).

Names appear verbatim in feedback — pick descriptive ones. This metric
data is recorded only (direction="record"), it does NOT contribute to
your score. Your score is a weighted combination of throughput
(dominant weight), bytes read from disk (`cgroup_iostat`), and
page-cache refaults (`cgroup_memstat`) — throughput matters most, but a
mutation that trades a small throughput loss for a much larger drop in
disk reads/refaults can still score better than one that only chases raw
throughput. Don't optimize for throughput alone and ignore the other two.

Choosing which listener(s) to attach to a feature:

  | You want...                              | Listener             |
  |-------------------------------------------|----------------------|
  | smallest/largest value ever seen          | MinMax               |
  | a trend weighted toward recent samples    | EWMA (set alpha)     |
  | the exact all-time average                | Average              |
  | last-K samples / a short-term rate         | RollingWindow (size) |

prefer combining listeners on an existing feature over anything else.

folio_evicted) already carries EWMA. Adding MinMax to the same feature is
a Tier 0 change — the feature itself is untouched:

        .ewma_alpha = 150,
    };
    ...
    s64 pressure_trend = vulcan_get_ewma(GF_EVICT_INTERVAL);
    s64 pressure_floor  = vulcan_get_min(GF_EVICT_INTERVAL);
    s64 pressure_ceil   = vulcan_get_max(GF_EVICT_INTERVAL);

Now the decision logic has a trend AND a range to combine, without a new
feature, new map, or new call site.

Counter-overhead note (reuses the cost model above): vulcan's own update
calls (`vulcan_folio_on_access`, `vulcan_update_feature`) are already
plain, non-atomic map writes — they follow the cheap convention by
construction. If you ALSO want a manual `g_*` counter to surface
vulcan-derived state via evo_dump, bump it from a naturally low-frequency
event (e.g. eviction), not from folio_accessed — that hot path runs once
per cache hit. An earlier version of the vulcan_recency seed had a
`g_promotions` counter incremented inside folio_accessed and it was
removed for exactly this reason. Prefer reading existing vulcan accessors
(`vulcan_get_ewma(GF_X)`, `meta->vulcan.access_count`) directly in your
feedback dump over adding a new counter that duplicates what a listener
already tracks.
