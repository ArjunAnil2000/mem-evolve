============================================================================
ALGORITHM & DATA-STRUCTURE SPACE (explore broadly)
============================================================================

Unlike the vulcan_bpf-based experiments in this project, this run's seeds
are hand-rolled BPF with no fixed feature set or listener scaffolding to
stay grounded in — you own the metadata structs, maps, and eviction logic
outright. Don't default to small parameter tweaks on the seed; trying a
structurally different eviction algorithm or a different metadata
representation is a first-class, encouraged move here, not a last resort
gated behind proving a small change first.

Concrete algorithms/data structures worth trying (illustrative, not
exhaustive — anything that respects Fatal Pitfalls C–G is in scope):
  * Multi-queue schemes: 2Q, S3-FIFO-style small/main/ghost queues, SLRU
    (segmented LRU), multi-level feedback queues.
  * Adaptive schemes: ARC/CAR (adaptively balance recency- vs.
    frequency-favoring queues using a ghost-list hit-rate signal), LRFU
    (a decayed blend of LRU and LFU).
  * Scan-resistant schemes: CLOCK with a second-chance bit, LIRS (track
    inter-reference recency to separate low-IRR pages from high-IRR
    one-time scanners), TinyLFU-style admission (only admit a new page if
    it's estimated hotter than the current eviction victim).
  * Frequency/probabilistic structures: a small Count-Min sketch or
    decaying counter map for approximate frequency estimation without
    exact per-page counts; sampling-based approximate LRU (sample K
    candidates via `bpf_for` with a compile-time bound, evict the coldest
    sampled) instead of maintaining an exact global order.
  * Cost-aware eviction: weight eviction priority by folio size
    (`folio_nr_pages`) so reclaim targets bytes freed, not just folio
    count.
  * Ghost lists / tombstones: keep lightweight metadata for recently
    evicted pages so a re-fault can be detected and used as a
    frequency/recency signal (2Q-style Ain/ghost handling), without
    re-inserting the actual folio into a live list.

The real constraints on structural ambition are Fatal Pitfalls D and E
(bounded loops/verifier limits, timeout budget) — design against those
directly, not against an artificial "keep it small" ceiling. A multi-list,
multi-phase policy that respects D and E is a perfectly good first
mutation; you don't need to first land a 10-line tweak before attempting
one.

Still worth doing before committing to a large rewrite:
  1. Sanity-check the new data structure's invariants (bounded sizes, no
     unbounded loops, every list entry reachable and freeable on both the
     access and eviction paths).
  2. Make sure Fatal Pitfall B's invariant (`if (!is_folio_relevant(folio))
     return;`) survives untouched — a new algorithm still must never
     manage non-watchlisted pages.
  3. If a structural rewrite fails to compile or times out, the next
     mutation should isolate and fix the specific piece that broke rather
     than discarding it for an equally large rewrite from scratch.

============================================================================
FATAL PITFALLS (READ BEFORE WRITING ANY CODE)
============================================================================

A. `is_folio_relevant(folio)` is NOT a hot/cold signal. It returns true
   for EVERY file under the watched directory — including scan files.
   Splitting into "hot_list" (relevant) vs "cold_list" (not relevant)
   gives zero separation. If you want to distinguish within watched
   pages, use a signal OTHER than `is_folio_relevant` — e.g., track
   access counts per inode, per-(inode,pgoff) metadata, reuse distance,
   or file size heuristics.

B. Do NOT manage non-watchlisted pages in your own BPF lists. Non-relevant
   folios are the benchmark process's binary / libc / anon pages; these
   CANNOT be evicted safely. Feeding them into your lists causes reclaim
   loops and full-timeout stalls. Always keep the seed's early return:
   `if (!is_folio_relevant(folio)) return;`

C. `INT64_MAX` is unavailable in BPF. Use `0x7fffffffffffffffLL` instead.

D. The BPF verifier rejects unbounded loops. All iteration must use
   `bpf_for` / `bpf_repeat` with a compile-time bound, or walk fixed
   struct chains. When in doubt, cap loops at 64 and early-exit.

E. Timeouts are a failure. A policy that hangs for 180s is strictly worse
   than one that scores near the seed.

F. BPF globals the loader reads via `skel->bss->NAME` MUST be declared as
   mutable (non-const, non-static-at-file-scope-with-initializer-only)
   and MUST actually be referenced by BPF code. Examples:

     // GOOD — lands in .bss, accessible as skel->bss->g_promotions
     __u64 g_promotions;           // file-scope, no initializer
     __u64 g_evictions = 0;        // initialized to 0 → still .bss

     // BAD — skel has no ->bss member; loader won't compile
     static const __u64 g_promotions = 0;   // const → .rodata
     // (or: variable declared but never used → optimized out entirely)

   If you introduce a counter, (1) declare it at BPF file scope without
   `const`, (2) increment it from at least one struct_ops handler, and
   (3) read it in the loader as `skel->bss->NAME`. Forgetting any of
   these three steps breaks the build or the counter read.

G. Never guess a `cache_ext_lib.bpf.h` identifier — this is the COMPLETE
   list, nothing else exists. Guessing a plausible-looking variant (e.g.
   inventing a "find which list this folio is in" lookup, because it
   sounds like it should exist) is a real, repeated cause of compile
   failures in this run — the compiler only warns
   ("implicit declaration of function ... invalid in C99"), it does NOT
   error at that point, and the resulting silent int-to-pointer coercion
   produces confusing follow-on errors instead of a clear "unknown
   function" message. Treat any `bpf_cache_ext_*` symbol not on this list
   as nonexistent, full stop:

   List kfuncs (exactly these eight, no others — there is NO
   `bpf_cache_ext_list_find`, NO `bpf_cache_ext_list_del_from`, NO
   generic "get the list a folio is on" lookup of any name):
     u64  bpf_cache_ext_ds_registry_new_list(struct mem_cgroup *memcg);
     int  bpf_cache_ext_list_add(u64 list, struct folio *folio);
     int  bpf_cache_ext_list_add_tail(u64 list, struct folio *folio);
     int  bpf_cache_ext_list_del(struct folio *folio);
     int  bpf_cache_ext_list_move(u64 list, struct folio *folio, bool tail);
     int  bpf_cache_ext_list_iterate(struct mem_cgroup *memcg, u64 list,
              int(iter_fn)(int idx, struct cache_ext_list_node *node),
              struct cache_ext_eviction_ctx *ctx);
     int  bpf_cache_ext_list_iterate_extended(struct mem_cgroup *memcg,
              u64 list, int(iter_fn)(int idx, struct cache_ext_list_node *node),
              struct cache_ext_iterate_opts *opts,
              struct cache_ext_eviction_ctx *ctx);
     int  bpf_cache_ext_list_sample(struct mem_cgroup *memcg, u64 list,
              s64(score_fn)(struct cache_ext_list_node *a),
              struct sampling_options *opts,
              struct cache_ext_eviction_ctx *ctx);
   `bpf_cache_ext_list_move` IS how you relocate a folio from one list to
   another (or reorder it within its current list) — use that for
   promotion/demotion, not a made-up "move if already present" variant.

   `struct cache_ext_list_node` (passed to your iterate callback) has
   EXACTLY two fields — `folio` and the internal `node` list_head, nothing
   else:
     struct cache_ext_list_node { struct folio *folio; struct list_head node; };
   There is NO `list_id`, `list`, or similar membership field on it —
   `node->list_id` (or any variant) is a compile error ("no member named
   ..."). If your policy needs to know which of ITS OWN lists a folio
   currently belongs to (e.g. "is this folio in probationary or
   protected?"), you must track that yourself as a field in your own
   per-folio metadata map (a bool or small enum you set on insert/promote/
   demote and check on lookup) — see vulcan_slru.c / vulcan_s3_fifo.c's
   `in_protected`/`in_main` field for the established pattern, even though
   those seeds are vulcan_bpf-based, the list-tracking idiom is identical.

   Callback return codes (exactly three, used by both list_iterate and
   list_iterate_extended):
     CACHE_EXT_CONTINUE_ITER  -- keep going; in list_iterate_extended,
                                  relocates the node to opts.continue_list
     CACHE_EXT_STOP_ITER      -- end the pass cleanly right now
     CACHE_EXT_EVICT_NODE     -- mark this folio for eviction; in
                                  list_iterate_extended, relocates the
                                  node to opts.evict_list first
   Any other return value is an error path in the kernel ("Unknown
   iterate return code") — do not return a raw int/bool, use these names.

   `struct cache_ext_iterate_opts` (only used with list_iterate_extended,
   exactly these six fields):
     struct cache_ext_iterate_opts {
         u64 continue_list;   // list id, or CACHE_EXT_ITERATE_SELF (0)
         u64 continue_mode;   // CACHE_EXT_ITERATE_HEAD or _TAIL
         u64 evict_list;      // list id, or CACHE_EXT_ITERATE_SELF (0)
         u64 evict_mode;      // CACHE_EXT_ITERATE_HEAD or _TAIL
         u64 nr_folios_continue;  // output: how many nodes continued
         u64 nr_folios_evict;     // output: how many nodes evicted
     };
   `CACHE_EXT_ITERATE_SELF` means "the list currently being iterated" —
   use it for `continue_list`/`evict_list` when you want a node to stay
   on the same list it came from, not a self-referential list handle.

POLICY METRICS — FEEDBACK CONVENTION (zero per-access overhead)
============================================================================

Your loader can dump named state to `$POLICY_METRICS_OUT` on exit. The
evaluator reads it and surfaces the values in next-round feedback under
`policy_counters:`. Use this to introspect your own state machine across
rounds without any workload cooperation.

The helper is in `evo_dump.h`. Pattern:

    // In USERSPACE LOADER section:
    #include "evo_dump.h"
    ...
    while (!exiting) sleep(1);

    FILE *m = evo_metrics_open();
    evo_dump_u64(m, "small_list_size",   skel->bss->small_list_size);
    evo_dump_u64(m, "main_list_size",    skel->bss->main_list_size);
    evo_dump_u64(m, "g_ghost_hits",      skel->bss->g_ghost_hits);
    evo_metrics_close(m);

    ret = 0;

Cost model — read carefully:

  * Each `evo_dump_u64(...)` is a single fread of an existing BPF global
    AT EXIT TIME. Zero per-access overhead. Surface as much as you want.
  * If you want event counts (evictions, promotions, ghost_hits), declare
    them as plain `__u64 g_NAME;` BPF globals and bump them in your hooks.
    This costs roughly one cache-line write per access on a single CPU —
    real, but small (much less than a hash-map lookup).
  * Do NOT add `__sync_fetch_and_add` on a shared global counter that
    every CPU touches — cross-CPU cache-line bouncing eats throughput.
    If you really need atomicity, use a per-CPU map; otherwise just live
    with the small race (counters are diagnostic, not state-of-truth).

Useful things to dump:
  * Sizes of any list/queue your policy maintains (`small_list_size`,
    `protected_list_size`, etc.).
  * Counters of events fired during the run (`g_evictions`, `g_ghost_hits`,
    `g_promote_skipped_unread`).
  * Tunables you want to confirm landed in `.rodata` correctly
    (`skel->rodata->cache_size`, `skel->rodata->small_target_pct`).

Names appear verbatim in feedback — pick descriptive ones. This metric
data is recorded only (direction="record"), it does NOT contribute to
your score. Your score is a weighted combination of throughput
(dominant weight), bytes read from disk (`cgroup_iostat`), and
page-cache refaults (`cgroup_memstat`) — throughput matters most, but a
mutation that trades a small throughput loss for a much larger drop in
disk reads/refaults can still score better than one that only chases raw
throughput. Don't optimize for throughput alone and ignore the other two.
